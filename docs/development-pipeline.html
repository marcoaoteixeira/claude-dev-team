development-pipeline

How the dev-team plugin takes one refined ticket (Jira or GitHub Issues) from design to a reviewed, QA-approved draft pull request — who's involved at each stage, what branches the flow, and what stops it from running away unattended.

Who's on the team

Which backend/frontend developer and reviewer actually get invoked depends on the project's detected stack (stack-detection) — the diagram below shows roles, not fixed agent names.

development-pipeline (conductor) software-architect ux-specialist (optional) qa-engineer backend developer/reviewer frontend developer/reviewer

The run

Stages run in order; the conductor enforces gates, loop caps and a time budget, and never writes production code, tests or design documents itself.

0

Start-up

conductor

Tracker detection (which MCP/CLI is connected — Jira or GitHub Issues), then load the ticket (needs testable acceptance criteria — not refined → stop). Repo preflight: clean working tree, default branch, stack detection (file markers, not a README claim — ambiguous or unsupported → ask or stop). Branch per delivery-conventions, write the state file.

Produces: branch, worktree, state.json (ticket, tracker, budget, detected stack)
1

Design

software-architect

Plan, API contract, work-split verdict (PARALLEL / BACKEND-FIRST / BACKEND-ONLY / FRONTEND-ONLY), ADRs when a decision qualifies, and a UX-spec-needed call.

1b · UX spec — only if the architect said YES: ux-specialist writes flows, states, interaction and accessibility specs the frontend developer builds against alongside the contract.
Produces: plan, contract, ADRs, UX spec (conditional)
2

Test cases

qa-engineer

From the ticket and the architect's plan/contract: backend and frontend case tables — acceptance coverage plus the failure modes that actually matter (dependency down, timeout, concurrency, auth).

Produces: agreed test cases, folded into each developer's brief
3

Build

backend developerfrontend developer

Test-first, per the architect's work-split verdict:

SplitShape
BACKEND-ONLY / FRONTEND-ONLYOne developer, one worktree.
BACKEND-FIRSTBackend built, reviewed and QA'd first; frontend follows in the same worktree.
PARALLELBackend and frontend launch together in separate worktrees (frontend builds on mocked contract), then merge and integrate once backend QA passes.
Produces: commits at green, per-developer report (DONE / NEEDS-DECISION / BLOCKED)
4

Review loop

capped at 3 rounds per side
backend reviewerfrontend reviewerux-specialist (design-QA)

Read-only diff review against the AC and contract. When a UX spec exists, ux-specialist design-QAs the built UI in the same round — its findings merge with the frontend reviewer's into one fix-findings pass, not two. A disputed finding goes to the reviewer in verify mode (fresh agent) to decide.

Produces: PASS or CHANGES-REQUIRED per side; lastReviewed commit recorded on pass
5

QA loop

capped at 2 rounds per side
qa-engineer

Verifies the agreed cases are actually proven by tests that run — not just present. CHANGES-REQUIRED sends the developer back in add-tests mode, then back through review.

Produces: APPROVED or CHANGES-REQUIRED per side
6

Review marker

conductor

Once every side is reviewed and QA-approved at the same commit, the conductor writes a signed marker. A later non-Markdown commit invalidates it automatically.

Produces: .claude/state/reviews/<branch>.json — the input the push-gate hook checks
7

Finalize

developerdeveloper

The developer whose work landed last updates CHANGELOG/README/guides, commits, pushes the branch, and opens a draft PR (pr-writer) — or saves it as a file if no PR token is configured.

Produces: pushed branch, draft PR (or saved PR file)
8

Clean up & report

conductor

Remove the worktree(s), print the Final Report: what was built, acceptance criteria → tests, documents, deviations, decisions taken on the user's behalf, open items.

9

Tracker hand-off

needs user approval
conductor

Only after the user explicitly approves — never an agent's verdict: posts a condensed summary comment on the ticket and moves it to Code Review (Jira transition, or a GitHub Projects v2 status move via gh).

Guard rails

Review-gate hook. require-review.cjs denies git push unless a passed review-and-QA marker exists for the exact commit being pushed. Direct pushes to the default branch are always denied.
Loop caps. Review: 3 rounds per side. QA: 2 rounds per side. Still failing past the cap → stop and report the open findings, never loop silently.
Time budget. Default 3h, resumable. At every stage boundary the conductor checks spent time against the budget and stops cleanly — committed work stays committed — rather than starting a stage it can't finish.
NEEDS-DECISION escalation. Scope/AC changes, conflicts with an accepted ADR, new external dependencies, destructive actions, and the stage-9 approval always go to the user — never answered by another agent's verdict.

Stack detection

Which developer/reviewer pair actually runs is resolved once, from file markers, not assumed and not read off a README that could be stale.

.NET backend

*.csproj, *.sln, or a global.json with an sdk key.

Kotlin/JVM backend

build.gradle.kts with Kotlin sources, no Android markers in the same module.

Angular frontend

angular.json.

Android frontend

build.gradle.kts and an AndroidManifest.xml under an app/module folder.

Ambiguous markers, an empty/new project, or a detected stack with no agent pair yet → the pipeline asks once or stops; it never substitutes the nearest existing pair.

Tracker detection

Which work tracker a ticket lives in is resolved once, from which tool is actually connected — not a declared setting that can go stale.

Jira

An Atlassian MCP tool is connected. Adapter: the plugin's existing Jira calls (unchanged).

GitHub Issues / Projects v2

The github MCP is connected and gh auth status succeeds with the project scope. Status moves (e.g. to Code Review) go through gh project item-edit, since the connected GitHub MCP server has no Projects-v2 tool.

Both connected, or neither → the pipeline asks once which tracker to use; it never guesses. A ticket on no Projects v2 board can still be read and commented on — only the status-move step needs the board.
